🔄 Модуль 2: Разбор CI/CD Автоматизации

CI/CD — это не какая-то одна сложная программа. Это концепция, конвейер, состоящий из скриптов-инструкций и распределенных сетевых роботов. В нашей экосистеме у каждого своя роль.

1. Распределение ролей в нашей инфраструктуре

💻 Локальная машина (Fedora в VirtualBox)

Наша домашняя мастерская. Здесь мы пишем человеческий текстовый код (HTML, Dockerfile) и отправляем его в архив командой git push.

🐱 GitHub и GitHub Actions (Архив и Сервер сборки — CI)

GitHub хранит наш код. Но когда прилетает пуш, его встроенный робот (Actions) просыпается и разворачивает в облаке Microsoft чистую, временную виртуалку ubuntu-latest. Прямо там, в облаке, робот скачивает наш код, читает Dockerfile и компилирует тяжелый готовый строительный блок — Docker-образ.

🐳 Docker Hub (Глобальный склад артефактов)

Сюда облачный робот GitHub выталкивает собранный образ (docker push). Наша Fedora не тратит свои ресурсы процессора на сборку «тяжелых» образов — она просто забирает со склада уже готовый продукт.

2. Как робот обходит закрытую домашнюю сеть (Модель Long Polling)

Наша Fedora находится за домашним роутером без белого IP-адреса. Как GitHub отправляет на неё команды деплоя (CD)?

GitHub НЕ ломится к нам домой. Наша Fedora сама держит дверь открытой.

Когда мы запустили агента (Runner), он сам инициировал исходящее HTTPS-соединение к серверам GitHub и повис на линии («замер» в ожидании). Когда на GitHub заканчивается сборка, он не ищет наш IP в интернете. Он просто скидывает текстовые команды в тот самый сетевой канал, который наша Fedora сама удерживает открытым.

3. Безопасность и Secrets

Наш репозиторий публичный. Чтобы не светить пароли, мы использовали вкладку Settings -> Secrets -> Actions. Мы сохранили секреты в запертый сейф GitHub, а в файле автоматизации сослались на них через переменные:

  • ${{ secrets.DOCKERHUB_USERNAME }} — Логин от склада.
  • ${{ secrets.DOCKERHUB_TOKEN }} — Защищенный токен доступа, заменяющий пароль.
